### Эндпоинт статистики

Реализован GET `/stats`, возвращающий статистику назначений:

- Количество PR открытых пров.
- Общее количество назначений по открытым PRам.
- Назначения по пользователям.
- Назначения по PRам.
  Структура ответа:

```
type Stats struct {
	TotalPRsCount    int                `json:"prs_count"`
	TotalAssignments int                `json:"assignments_count"`
	UserAssignments  []*UserAssignments `json:"user_assignments"`
	ReviewsPR        []*ReviewsPR       `json:"pr_reviews"`
}

type UserAssignments struct {
	UserID           string `json:"user_id"`
	Username         string `json:"username"`
	AssignmentsCount int    `json:"assignments_count"`
}

type ReviewsPR struct {
	PullRequestID   string `json:"pull_request_id"`
	PullRequestName string `json:"pull_request_name"`
	ReviewersCount  int    `json:"reviewers_count"`
}

```

### Эндпоинт `/users/setIsActive`

Не сказано, что делать, если этого пользователя есть PR на ревью.
Добавлено поведени пользователь становится неактивным, то все его **открытые** (мержнутые PR не снимаем,
так как система, как будто, предполагает хранение подобной истории) PR снимаются с его ревью.
Переназначения не происходит, так как ручка просто про флаг активности, а не деактивации и переназначения.е: если
Для кейсов, когда это требуется есть ручка для массовой деактивации пользователей с переназначением

### Эндпоинт `/users/getReview`

Не возвращает `NotFound` при передаче несуществующего пользователя, так как для этого потребовалось бы:

1. JOIN с таблицей пользователей
2. Дополнительный запрос к базе данных
   Принято решение возвращать пустой список для упрощения логики.

### Эндпонинт `/team/deactivateMembers`

Этот эндпоинт предназначен для массовой деактивации пользователей в рамках одной команды. Помимо установки флага
`isActive = false` для указанных пользователей, он также выполняет безопасное переназначение всех открытых Pull
Request'ов, которые были на них назначены.

**Security**: `Admin`

**Тело запроса**:

```json
{
  "team_name": "payments",
  "users": [
    "u1",
    "u2"
  ]
}
```

#### Логика работы:

Вся операция выполняется в рамках одной транзакции для обеспечения атомарности и целостности данных
Данная операция идемпотентна

1. **Поиск кандидатов**: Определяется пул потенциальных ревьюеров. В него входят все **активные** члены той же команды,
   которые **не попали** в список на деактивацию
2. **Поиск PR для переназначения**: Система находит все **открытые** PR'ы, где в качестве ревьюеров числятся
   деактивируемые пользователи
3. **Переназначение**:
    * Для каждого такого PR определяется, сколько ревьюеров выбывает
    * Из пула кандидатов подбирается необходимое количество новых ревьюеров
    * Переданные пользователи снимаются со всех открытых PR, а новые назначаются
4. **Деактивация**: После успешного переназначения PR, у всех пользователей из исходного списка обновляется статус на
   `isActive = false`
   Если на каком-либо этапе происходит ошибка, вся транзакция откатывается, и никаких изменений в базе данных не
   сохраняется

#### Возникшие проблемы

Дедлок при попытке деактивировать нескольких пользователей одновременно.
**Решение**: Сортировка списка пользователей по алфавиту перед началом транзакции для обеспечения последовательного
порядка блокировок записей в бд + ретраи на такие транзакции.
**НО** эндпоинт все так же может отдавать ошибки, в случае когда много запросов пытаются деактивировать одинаковые
команды, так как блокировка на строки берется и выходит дедлок, который мы пробуем заретраить, но это может не получится

### Краткое описание быстродействия и безопасности
Сервис оптимизирован для умеренных нагрузок: до 50 команд с средним количеством участников 20 человек на команду и
примерно 10 PR на человека. При средней нагрузке время ответа основных эндпоинтов составляет около 20 мс
Единственный эндпоинт, который может отрабатывать дольше (до 100 мс при средних объемах данных), — это массовая
деактивация пользователей (/team/deactivateMembers), логика которого описана выше
